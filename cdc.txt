# Feature — Envoi en masse

> Note de nommage : la feature s'appelle « Envoi en masse » côté UI
> (français). Côté code (tables Prisma, types, services), tous les
> identifiants sont en anglais. Mapping :
>
> - « envoi » → `Broadcast`
> - « envoi perso » (1 destinataire) → `BroadcastRecipient`
> - « template » → `MessageTemplate`
> - « type d'envoi » (mail/sms) → `channel`

## 1. Contexte & objectif

Permettre à l'admin de Jump de créer des **templates** (mail / SMS) puis de
les envoyer à un sous-ensemble ciblé d'utilisateurs (talents, parents, staff),
avec **suivi par destinataire** (envoi, ouverture via clic sur lien tracké),
et de **consulter l'historique** des envois reçus par un talent depuis
l'espace Dev.

V1 = brouillon + envoi immédiat, pas d'annulation, pas de programmation.

## 2. Périmètre V1

- Création / édition / suppression de templates (mail HTML, SMS texte).
- Création d'un envoi : sélection template + audience + (optionnel) event.
- Aperçu live + bouton **« S'envoyer un test »** avant validation.
- Envoi immédiat, file de jobs côté serveur.
- Historique des envois (statut global) + détail par destinataire
  (`BroadcastRecipient` : envoyé, ouvert).
- Vue dans la fiche d'un talent (espace Dev) : liste de ses envois personnels.

**Hors scope V1** : programmation différée, annulation en cours, A/B testing,
statistiques agrégées (taux d'ouverture par template, etc.), réponses entrantes.

## 3. Permissions

- Menu **« Envoi en masse »** (icône `paperPlane`) sous `/staff/admin/`.
- Accès réservé au rôle `admin` (groupe à ajouter dans `STAFF_GROUPS` si
  besoin, ou simple gate sur `staffRole === 'admin'`).
- Aucun accès staff dev / peda / manta à la création ou à l'envoi.
- Lecture seule (vue par talent) : disponible côté Dev sur la fiche talent.

## 4. Onglet « Templates »

### Définition

Un template a :

| Champ      | Type                | Obligatoire | Notes                              |
| ---------- | ------------------- | ----------- | ---------------------------------- |
| `name`     | string              | oui         | identifiant lisible interne        |
| `channel`  | `mail` \| `sms`     | oui         | immuable après création            |
| `subject`  | string              | mail: oui / sms: facultatif (interne uniquement) | gabarit avec variables |
| `body`     | string              | oui         | mail: HTML / sms: texte 160 c. max |
| `createdAt`, `updatedAt`, `createdById` | — | — | audit                       |

### Variables disponibles

Affichées dans l'éditeur (autocomplétion + indication), substituées
au moment de l'envoi :

**Variables destinataire (mail & sms)**

- `{{prenom}}` — prénom du destinataire
- `{{nom}}` — nom du destinataire
- `{{email}}` — email du destinataire
- `{{phone}}` — téléphone du destinataire
- `{{campus}}` — nom du campus du destinataire

**Variables de contexte d'envoi**

- `{{event_name}}` — nom de l'event lié à l'envoi (vide si non lié)

**Variables d'auth — générées par destinataire au send**

- `{{fastlogin_link}}` — lien de connexion magique unique (token BetterAuth,
  TTL à définir, ex. 7 jours)
- `{{otp_code}}` — code OTP 6 chiffres à usage unique (TTL court, ex. 10 min)

> Ces variables ne sont **pas** disponibles dans l'aperçu — elles sont
> remplacées par des valeurs fictives clairement marquées (`[OTP_DEMO]`,
> `https://jump.epiboost.fr/fastlogin?token=DEMO`).

### Éditeur

- Mail : éditeur WYSIWYG (TipTap, déjà en dépendance) + bascule vue HTML brute.
- SMS : `<textarea>` simple avec compteur de caractères (max 160, GSM-7 par
  défaut, alerte si caractères Unicode qui font passer en 70 c./SMS).

### Aperçu

Panneau live à droite de l'éditeur, rempli avec un destinataire fictif :

```
Prénom: Jean, Nom: Dupont, Campus: Paris, Event: Coding Club n°4
```

## 5. Onglet « Envois »

### Création d'un envoi

| Champ          | Type                                                          | Obligatoire        |
| -------------- | ------------------------------------------------------------- | ------------------ |
| `name`         | string (interne, ex. « Mail invitation Coding Club avril »)   | oui                |
| `channel`      | `mail` \| `sms`                                               | oui (déduit du template) |
| `templateId`   | ref MessageTemplate                                           | oui                |
| `campusId`     | ref Campus (un seul)                                          | oui                |
| `audience`     | `talent` \| `parent` \| `dev` \| `peda` \| `manta` \| `superdev` | oui             |
| `eventId`      | ref Event (un seul) ou `null` = « tous les events du campus » | si audience ∈ {talent, parent, manta} |
| `filters`      | filtres avancés (cf. §5.2)                                    | facultatif         |

### 5.2 Filtres avancés (audience = talent / parent)

Builder de filtres combinables (AND) :

- Niveau scolaire (`niveau` : 6e..Terminale, Sup) — multi-sélection
- Charte signée : oui / non / indifférent
- Droit à l'image signé : oui / non / indifférent
- Niveau Jump (`Novice` / `Apprentice` / `Expert`)
- A déjà participé à un event : oui / non / indifférent
- Inscrit à au moins un event à venir : oui / non / indifférent

> Pour `parent`, la résolution du destinataire utilise `parentEmail` /
> `parentPhone` du talent ciblé.

### 5.2.bis Retargeting — repartir d'un envoi passé

Cas d'usage type : « relancer les talents à qui j'ai envoyé l'invitation
au Coding Club mais qui ne l'ont pas ouverte ».

Dans le formulaire d'envoi, option **« Repartir d'un envoi passé »** :

| Champ                | Type                                            |
| -------------------- | ----------------------------------------------- |
| `sourceBroadcastId`  | ref Broadcast (sélecteur paginé, plus récents d'abord) |
| `sourceFilter`       | `opened` \| `not_opened` \| `all`               |

Quand cette option est activée :

- L'**audience de base** = les `BroadcastRecipient` du `sourceBroadcastId`,
  filtrés selon `sourceFilter` :
  - `opened` : `openedAt IS NOT NULL` (= a cliqué sur ≥ 1 lien tracké)
  - `not_opened` : `openedAt IS NULL`
  - `all` : tous (équivalent à recopier la même liste de destinataires)
- Le champ `audience` (talent / parent / staff) reste sélectionnable et
  agit comme un **filtre supplémentaire** sur la résolution du
  destinataire (ex. `sourceFilter = not_opened` + `audience = parent` →
  contacter les parents des talents qui n'ont pas ouvert).
- Les filtres avancés §5.2 (niveau, charte, etc.) restent applicables
  par-dessus, en AND.
- `campusId` est pré-rempli avec celui de l'envoi source mais reste
  modifiable (utile si on veut restreindre à un sous-campus).

> **Limitation V1** : « ouverture » = clic sur un lien tracké uniquement.
> Pas de pixel d'ouverture mail, donc un destinataire qui a bien reçu et
> lu le mail mais n'a pas cliqué est compté comme `not_opened`. À
> documenter dans l'UI à côté du filtre.

> **SMS source** : le tracking s'applique automatiquement à toute URL
> présente dans le corps (cf. §6 « SMS »), donc `opened` / `not_opened`
> ont du sens dès qu'il y a au moins un lien dans le SMS source.

### 5.3 Prévisualisation des destinataires

Une fois tous les champs renseignés :

- Liste paginée des destinataires résolus (prénom, nom, email/phone, campus).
- Compteur total bien visible (« 142 destinataires »).
- Indicateurs d'exclusion : destinataires sans email (mail) ou sans
  téléphone (sms) listés à part avec compte et raison (filtrés
  automatiquement à l'envoi).

### 5.4 Test send

Bouton **« S'envoyer un test »** :

- Envoie le message rendu à l'admin connecté (`locals.user.email` ou
  numéro de test à saisir pour SMS).
- Variables remplacées par des valeurs factices identiques à celles de
  l'aperçu (mais réelles côté provider : utile pour vérifier rendu mail
  chez Gmail/Outlook, encodage SMS).

### 5.5 Validation & exécution

Bouton **« Valider l'envoi »** :

- Crée un `Broadcast` en statut `queued`.
- Push un job dans la queue d'envoi (un job = un `BroadcastRecipient`).
- Pas d'annulation possible une fois validé.

### 5.6 Historique

Liste paginée des envois passés, tri par date desc :

| Colonne                  | Détail                                                       |
| ------------------------ | ------------------------------------------------------------ |
| Nom                      |                                                              |
| Canal                    | mail / sms                                                   |
| Template                 | lien vers le template (immuable cf. §5.7)                    |
| Campus                   |                                                              |
| Event                    | si renseigné                                                 |
| Date d'envoi             | timestamp de validation                                      |
| Statut                   | `queued`, `sending`, `sent`, `partial_failed`, `failed`      |
| Progression              | `n_sent / n_total` + `n_failed` + `n_opened`                 |

Détail d'un envoi → liste de tous les `BroadcastRecipient` (statut
individuel, ouverture).

### 5.7 Immutabilité des templates utilisés

Quand un envoi est validé, on **snapshot** le sujet et le corps du template
dans le `Broadcast` (champs `subjectSnapshot`, `bodySnapshot`). Modifier le
template par la suite ne change pas l'historique.

## 6. Tracking des ouvertures

### Principe

Tout lien `<a href="https://...">` dans le corps mail est **réécrit
automatiquement côté serveur** au moment de l'envoi :

```
https://jump.epiboost.fr/fastlogin?token=xxx
  → https://jump.epiboost.fr/fastlogin?token=xxx&tracking_id=<broadcast_recipient_id>
```

L'auteur du template n'a **rien** à faire — pas de `{{tracking_id}}` à
insérer manuellement.

### Mécanique

- Réécriture serveur : parser le HTML, itérer sur les `<a href>`, ajouter
  le query param `tracking_id`. Pour les URLs déjà absolues hors domaine
  Jump (ex. `https://google.com`), même traitement (l'ouverture = clic
  sortant compte aussi).
- Endpoint middleware : un hook léger qui, sur n'importe quelle requête
  avec `?tracking_id=...`, déclenche un `UPDATE BroadcastRecipient SET
  openedAt = COALESCE(openedAt, now()) WHERE id = ?` sans écraser si déjà
  ouvert. L'effet de bord est invisible pour l'utilisateur (pas de
  redirect supplémentaire).

### SMS

Réécriture par **regex** sur le corps texte au moment de l'envoi :

- Détecter toute URL (`https?://...`) avec une regex robuste (gérer les
  caractères terminaux à exclure : `.`, `,`, `)`, etc. — ex. `https://
  example.com.` → match `https://example.com`, garder le `.` final hors
  URL).
- Pour chaque URL trouvée, ajouter `?tracking_id=<broadcast_recipient_id>`
  (ou `&tracking_id=...` si l'URL a déjà un query string).
- Comportement identique au mail : tout lien est tracké, qu'il pointe
  vers Jump ou un domaine externe.

**Impact sur la longueur** : un `tracking_id` cuid (~25 caractères) +
`&tracking_id=` ajoute ~40 caractères par lien. Le compteur de
caractères de l'éditeur SMS (§4 « Éditeur ») doit afficher la longueur
**après** réécriture estimée (avec un placeholder de la bonne longueur),
pour éviter qu'un SMS qui semble tenir en 160 c. déborde en 2 segments
une fois envoyé.

### Modèle de données

`BroadcastRecipient` représente un destinataire d'un envoi :

| Champ              | Type            | Notes                                            |
| ------------------ | --------------- | ------------------------------------------------ |
| `id`               | cuid            | sert de `tracking_id`                            |
| `broadcastId`      | ref Broadcast   |                                                  |
| `talentId`         | ref Talent?     | si destinataire est un talent                    |
| `staffUserId`      | ref bauth_user? | si destinataire est un membre du staff           |
| `parentOfTalentId` | ref Talent?     | si destinataire est un parent (résolu via talent)|
| `eventId`          | ref Event?      | event lié si applicable                          |
| `campusId`         | ref Campus      |                                                  |
| `recipientEmail`   | string?         | snapshot — l'email réellement utilisé            |
| `recipientPhone`   | string?         | snapshot — le tél réellement utilisé             |
| `status`           | enum            | `pending`, `sent`, `failed`                      |
| `errorMessage`     | string?         |                                                  |
| `sentAt`           | datetime?       |                                                  |
| `openedAt`         | datetime?       | timestamp 1er clic — non écrasé                  |

## 7. Vue espace Dev — fiche talent

Sur la fiche d'un talent dans `/staff/dev/students/[id]`, ajouter une
section **« Communications »** :

- Liste des `BroadcastRecipient` où `talentId === talent.id` OU
  `parentOfTalentId === talent.id` (distinguer visuellement : « envoyé au
  talent » / « envoyé au parent »).
- Tri date desc, pagination.
- Colonnes : date, canal, nom de l'envoi, sujet, statut, ouvert (oui/non).
- Clic sur une ligne → modal avec le rendu (sujet + corps snapshot).

## 8. Modèle de données — proposition Prisma

```prisma
enum BroadcastChannel {
  mail
  sms
}

enum BroadcastStatus {
  queued
  sending
  sent
  partial_failed
  failed
}

enum BroadcastRecipientStatus {
  pending
  sent
  failed
}

enum BroadcastAudience {
  talent
  parent
  dev
  peda
  manta
  superdev
}

enum BroadcastSourceFilter {
  opened
  not_opened
  all
}

model MessageTemplate {
  id          String           @id @default(cuid())
  name        String
  channel     BroadcastChannel
  subject     String?
  body        String
  createdById String
  createdAt   DateTime         @default(now())
  updatedAt   DateTime         @updatedAt

  broadcasts Broadcast[]

  @@index([channel])
}

model Broadcast {
  id                 String                  @id @default(cuid())
  name               String
  channel            BroadcastChannel
  templateId         String
  campusId           String
  audience           BroadcastAudience
  eventId            String?
  sourceBroadcastId  String?                 // §5.2.bis — retargeting
  sourceFilter       BroadcastSourceFilter?  // requis si sourceBroadcastId non null
  filters            Json?                   // builder de filtres §5.2
  subjectSnapshot    String?
  bodySnapshot       String
  status             BroadcastStatus         @default(queued)
  createdById        String
  createdAt          DateTime                @default(now())

  template        MessageTemplate      @relation(fields: [templateId], references: [id])
  campus          Campus               @relation(fields: [campusId], references: [id])
  event           Event?               @relation(fields: [eventId], references: [id])
  sourceBroadcast Broadcast?           @relation("BroadcastRetargeting", fields: [sourceBroadcastId], references: [id])
  retargets       Broadcast[]          @relation("BroadcastRetargeting")
  recipients      BroadcastRecipient[]

  @@index([campusId])
  @@index([eventId])
  @@index([sourceBroadcastId])
  @@index([createdAt])
}

model BroadcastRecipient {
  id                String                   @id @default(cuid())
  broadcastId       String
  talentId          String?
  staffUserId       String?
  parentOfTalentId  String?
  eventId           String?
  campusId          String
  recipientEmail    String?
  recipientPhone    String?
  status            BroadcastRecipientStatus @default(pending)
  errorMessage      String?
  sentAt            DateTime?
  openedAt          DateTime?
  createdAt         DateTime                 @default(now())

  broadcast Broadcast  @relation(fields: [broadcastId], references: [id], onDelete: Cascade)
  talent    Talent?    @relation("BroadcastRecipientTalent", fields: [talentId], references: [id])
  parentOf  Talent?    @relation("BroadcastRecipientParent", fields: [parentOfTalentId], references: [id])

  @@index([broadcastId])
  @@index([talentId])
  @@index([parentOfTalentId])
  @@index([openedAt])
}
```

## 9. Infra & dépendances

- **Mail** : provider existant (Resend, déjà en place pour les OTP).
- **SMS** : provider non décidé. Définir une interface
  `SmsProvider { send(to, body): Promise<void> }` et brancher l'impl
  plus tard (Twilio, OVH SMS, etc.). Variable d'env `SMS_PROVIDER` pour
  switcher.
- **Queue** : réutiliser le pattern de jobs existant (cf. `/api/jobs/*`).
  Un broadcast = N jobs `BroadcastRecipient`. Concurrence limitée pour
  respecter les rate limits du provider.
- **Réécriture HTML** : utiliser un parser robuste (`cheerio` ou
  `node-html-parser`) — pas de regex sur du HTML.

## 10. Sécurité & RGPD

- **Mineurs** : ne pas envoyer à un talent qui n'a pas signé la charte
  (filtre implicite côté backend, même si l'admin coche « tous »).
- **Désinscription mail** : prévoir un footer auto-injecté avec
  mention légale + lien de désinscription (V1 minimal : adresse de
  contact ; V2 : vrai mécanisme d'opt-out).
- **Snapshot emails/phones** : conserver `recipientEmail` /
  `recipientPhone` sur `BroadcastRecipient` permet de tracer ce qui a
  été envoyé même si le profil change ensuite. Inclure dans la purge
  RGPD (`anonymizationService`) en parallèle des données du talent.
- **Tokens magic-link / OTP** : à usage unique, TTL court, stockés via
  BetterAuth.

## 11. Points ouverts à trancher

1. **TTL du `fastlogin_link`** : 7j ? Configurable par envoi ?
2. **Footer mail obligatoire** : qui rédige le contenu légal (mentions,
   désinscription) ? Hardcodé dans le code ou éditable en admin ?
3. **Quota / rate limit côté envoi** : à quel rythme on dépile la queue
   pour rester sous les limites Resend (et futur SMS provider) ?
4. **Que faire si un destinataire apparaît plusieurs fois** (ex. parent
   ayant plusieurs enfants dans la cible) : 1 envoi par enfant ou
   dédoublonnage ?
5. **Variables manquantes** : si un template utilise `{{event_name}}`
   et que l'envoi n'a pas d'event lié, on remplace par vide, par une
   valeur par défaut, ou on bloque la validation ?
