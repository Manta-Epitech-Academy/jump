# Staff cohort tables

Two hard-won contracts govern every staff list page over cohort volume (~200 rows). Both were
performance regressions that shipped once; do not reintroduce either shape. A third section, at the
bottom, lists the mechanics these pages already share: reach for those before writing your own.

## Streaming heavy staff tables

The dev stage-seconde pages (`inscrits`, `émargement`, `closings`, `bilan`) and the admin directories (`talents`, `notes`, `closing-pdfs`, `feedback-forms`, `sf-conflicts`) stream their cohort. The `load` awaits only cheap shell data (event, countdown, filter chips) and returns the heavy cohort as a single **un-awaited promise**; the page renders its shell instantly and resolves the results region from that promise, showing the shared `ResultsSkeleton` (`$lib/components/staff/ResultsSkeleton.svelte`) until it lands. Follow this for any new staff table over cohort volume (~200 rows): do not `await` the heavy query in `load`, or you block the client navigation on it (the felt-2s "dead click").

- **Plain `{#await data.cohort}`** for pages that are genuinely read-only, where nothing ever replaces the promise (inscrits, closings, bilan): there is no reflash to prevent and no reason to hold a second copy of the payload.
- **Hold the promise with `createStreamedCohort` instead** when the page polls, writes optimistically, or re-navigates for its own filters (émargement, admin talents / notes / closing-pdfs / feedback-forms / sf-conflicts). Binding `{#await}` directly there means every `invalidate`, optimistic write or filter navigation builds a fresh promise, which reflashes the skeleton and remounts the child, wiping its local state (search, optimistic overrides). `createStreamedCohort(() => data.cohort)` holds the last resolved value behind `.value` / `.failed`, with the stale-promise guard that drops a resolution arriving after a newer navigation. Do **not** hand-roll that guard: six pages had their own copy of it and one had lost its `catch`, which left a failed load showing "Chargement…" forever.
- **Keep SSR on.** Streaming renders the shell server-side and flushes the cohort over the same response; the win is a fast first paint of the chrome, not a blank-until-JS page. Do not reach for `export const ssr = false` to "simplify" - it regresses first paint and buys nothing here.
- `ResultsSkeleton` is **delay-gated** (held invisible ~180ms, height reserved) so warm navigations swap straight to content without a skeleton flash; only genuinely slow loads fade it in. Reuse it, do not hand-roll per-page pending markup.

## SortableTable renders one layout

`SortableTable` (`$lib/components/staff/datatable/`) renders **either** the desktop table **or** the `mobileRow` cards, gated by a `MediaQuery` (lg seam) plus a mount guard, never both at once. Do not reintroduce a CSS-toggled (`hidden lg:block` / `lg:hidden`) dual render: it builds and hydrates every row twice (2x DOM nodes, 2x avatars) and was the main client-side render cost on these tables. Pages without a `mobileRow` snippet always render the desktop table (unchanged).

Column headers get their treatment from `Table.Head`, not from the page: it carries the mono overline, so a sentence-case header is not a variant to reach for. `TalentAvatar` draws its monogram locally; it used to fetch one per row from a third party, which sent a minor's id off-site and cost a request each time.

## What already exists once

These pages are near-identical by design, so their mechanics live in one place each. Adding a staff
list page means wiring these up, not rewriting them; a behaviour that differs between two lists is a
bug in one of them, not a local preference. Each module's own doc comment carries the rule it
enforces and the divergence that earned it.
