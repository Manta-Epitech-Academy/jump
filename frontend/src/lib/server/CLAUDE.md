# Key Server Services

- **`auth.ts`**: BetterAuth config (Prisma adapter, Microsoft OAuth, email OTP, admin plugin with impersonation)
- **`adminApi/`**: curated admin API: token auth (tier + write capability), audit log with before/after, operation catalogue, write implementations, two-step plan digest, MCP server (see above)
- **`services/adminStats/`**: the curated aggregates (cohort profile, school reach and lycée churn, the cross-campus comparison, closing insights and testimonials, feedback results, engagement, onboarding funnel and velocity, compliance, the operational queues, configuration state, the school-year review), each figure carrying its definition
- **`services/adminDigest.ts`**: weekly French digest to every admin-role login, built on `adminStats/`
- **`services/staffAdminService.ts`**: staff roster writes for `/staff/admin/users` (the role change moves `StaffProfile.staffRole` + `bauth_user.role` in one transaction)
- **`services/syncErrorService.ts`**: admin remediation of sync errors, including the extId rebind and its refusal branches
- **`services/onboardingService.ts`**: the onboarding transactions: parent-1 account provisioning, interest swap, rules signature (timestamps + XP facts + PDF job)
- **`infra/documentRenderer.ts`** - the one browser-render path: PDFs for what gets printed, PNGs for what gets looked at, both over the same page setup so a preview cannot disagree with the document it previews. Owns the page lifecycle and turns off **both script execution and the network**, so no caller can render a stored design with either switched off by forgetting to switch it on; no template wants page JS anyway (a QR code arrives as a data URI its caller built). Fonts therefore carry their own bytes (`templates/fonts.ts`, `@font-face` built from the `@fontsource` packages with `?inline`)
- **`services/diplomaGenerator.ts`** - certificates: takes the design off a `Diploma_Template` row, substitutes the `{placeholders}`, and renders one page per recipient
- **`services/syncService.ts`**: what the Salesforce worker pushes → events (campus per row, never deleted), talent identities (seeds `Talent`, upserts the `TalentSfImport` mirror, no-clobber; see Salesforce reconciliation), and enrolments, whose prune runs on a `full` pass only and only from a complete roster (anything else is held on `Sync_PruneHold`, never refused)
- **`services/devSpaceVisibility.ts`**: which Salesforce statuses each event's dev space shows (`EventConfig_ShownStatus`, against the `Sync_MemberStatus` catalogue it is also the one writer of), and the one place outside the sync that writes the `Participation.shownInDevSpace` projection every dev count and list filters on
- **`services/syncConfigService.ts`**: what the worker is told on every tick, and the campus join that keeps a generated database out of every sync's scope
- **`services/syncRunService.ts`**: the run ledger, the watermarks projected off it (`MAX(finishedAt)` over successful runs, so a failure replays its window), and its own retention
- **`services/workshopService.ts`**: the CTFd activities a talent is offered and what CTFd reports back. One rule decides which (`selectWorkshopOfferings` in `domain/workshops.ts`: from the offering event's first campus day, for good afterwards), and both the dashboard and the entry action read it, so a hidden activity is never one hand-made POST away. Turns a signed progress callback into the one XP grant per (talent, activity). An activity is the CONTENT a CTFd host serves (`Workshop_Activity`), not the host (`Workshop_Instance`), because a host serves one content after another: the participation, the grant and the name in the timeline belong to what the talent walked. The callback names both, and is filed only when that content is an activity this very host serves; one that names none is refused, so an instance older than the field resends once upgraded instead of being filed under a guess. What the dashboard celebrates afterwards is that grant minus `xpCelebrated`, the amount already shown, never a counter of its own: a counter fed by deltas once announced several times what the profile gained, because concurrent callbacks and a progress falling then climbing back each added to it. The entry ticket names the session the participation was pinned to on first entry (never the enrolment that let the talent in today), which is the session the plugin files the CTFd account under and keeps to itself: an instance serves several events over its life (reused by a campus from one request to the next, shared by a season's camps, kept up for a flagship subject), and a talent is ranked among their own event only. A host moving on to another content is a new activity on the same instance, declared with `write_workshop_activity`, its slug the one the instance shows for that content. And an instance asks which of its accounts belong to erased talents (`/api/workshops/erasures`) rather than being told: the answer is read off `Talent.anonymizedAt` every time, so an instance that was down catches up on its next question, and an id Jump does not know is held, never reported erased.
- **`images/remote.ts`**: a picture an admin points Jump at (an activity's cover, a highlighted event's picture, the pictures a campus note names, a feedback form's persona icon), downloaded at write time and COPIED into storage, never linked to: a minor's browser fetches nothing from another host. **It takes what the admin gives**: any proportion and any size, still or animated, an animation getting a derived still for reduced motion; laying a picture out is the page's job (`CopiedPicture` bounds it), and a shape was never a reason to refuse one. What it refuses protects somebody else: it connects only to a public address (`infra/publicAddress.ts`), judged on the address actually dialled so a name cannot resolve elsewhere behind the check, and every redirect hop is a request checked the same way and may not leave https; it reads no further than the size cap, sniffs the bytes rather than trusting the name, refuses an animation too heavy for a phone and a canvas too large for the pod, and names the reason. `replacePictures` keeps the copy of an address a row already holds rather than downloading it again, and swaps stored keys so a row never points at nothing. All are authored over the API (`write_workshop_cover`, `write_talent_home_highlight`, `write_talent_home_note`, `write_feedback_form`); a cover is never read from CTFd. The persona icon is the one copy kept as a still (`feedbackForms/personaIcon.ts`, the first frame of an animation): it is served as WebP at the size of a chat avatar, and the builder's upload takes stills too
- **`services/talentHomeService.ts`**: what a talent's home shows of their campus (« le mot du campus », the one message of its Actualités card, and the highlighted event to sign up for). Both are authored campus by campus over the admin API (`adminApi/writes/talentHome.ts`), never derived; this reads them for the campus the request hooks resolved, renders the note through `renderAuthoredMarkdown`, drawing each picture it names from Jump's copy and never from the address written, and drops a highlight whose day has passed on the campus clock. What the home's blue hero then suggests (the day's activity, else the open highlight, else an activity to carry on at home, else nothing) is one pure rule, `pickHomeHero` in `domain/talentHome.ts`, so the hero never holds two suggestions of the same weight
- **`services/reconciliationService.ts`**: computes `Talent` ↔ `TalentSfImport` conflicts; accept/reject + CSV for `/staff/admin/sf-conflicts`
- **`services/schoolService.ts`** / **`annuaire.ts`**: lazy `School` resolution from UAI via the éducation-nationale annuaire
- **`services/anonymizationService.ts`**: RGPD anonymization job
- **`infra/browserPool.ts`**: pooled Puppeteer instances (max 5 concurrent, 60s idle timeout)
- **`usage/record.ts`**: the one usage recorder: fire-and-forget, server-only, composes the dedupe key, honours a talent's objection, and refuses rather than guesses when the salt is unset
- **`usage/rollup.ts`**: folds the monthly cube then purges the raw window, in that order
- **`services/adminStats/featureUsage.ts`** / **`staffActivity.ts`**: feature adoption per campus, and whether the team logs in at all
- **`usage/memberActivity.ts`**: the one named-member read, for the dialog on `/staff/admin/users`. Deliberately not an operation: `ops_staff_activity` answers the same question in counts with no names, and a named-member read reachable with a token would put per-employee behaviour behind a credential minted for figures
- **`db/scoped.ts`**: campus-scoped DB query helpers
- **`db/textSearch.ts`**: the one way a search box queries the database: word by word, each word matching some field (`talentIdentityMatches` for a talent), never the whole query against one column, which is how "Prénom Nom" found nobody (#360). The in-memory lists use its twin, `components/staff/datatable/search.ts`
